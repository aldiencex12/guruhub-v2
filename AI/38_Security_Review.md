## 1. Multi-Tenant Security & Isolation Protocol

Multi-tenancy isolation is enforced through a **Triple-Layer Defense Strategy**:

1. **Layer 1 (Middleware HTTP Guard):** `authMiddleware` extracts `x-school-id` from validated JWT claims and attaches `schoolId` to the request context store. Client-supplied header overrides are strictly ignored.
2. **Layer 2 (Service Guard):** Every domain service method accepts `schoolId` as an explicit first parameter. Cross-tenant parameter passing is rejected with a `ForbiddenError`.
3. **Layer 3 (Database SQL Guard):** Every SQL query generated by `DisciplineRepository` mandates `eq(table.schoolId, schoolId)`. SQL execution without a `school_id` filter is prohibited.

## 3. Threat Matrix & Countermeasures

### 3.1 Race Conditions & Duplicate Report Submissions
- **Threat:** A user rapidly clicks "Submit Incident Report" twice, causing double demerit entries.
- **Countermeasure:** Redis distributed idempotency locking (`idempotency:incident:{schoolId}:{userId}:{hash}`) locks submission keys for 10 seconds. Duplicate payloads within 10 seconds return HTTP 409 Conflict.

### 3.2 Privilege Escalation on Status Approval
- **Threat:** A teacher attempts to approve (`VERIFY`) their own reported incident without BK authorization.
- **Countermeasure:** `PUT /incidents/:id/status` enforces `requireRoles(["SuperAdmin", "SchoolAdmin", "Principal"])` in the route handler.

### 3.3 Malicious Attachment Uploads
- **Threat:** An attacker uploads a web shell (`shell.php`) disguised as an incident photo evidence.
- **Countermeasure:** Strict MIME type checking, magic byte header inspection (`image/jpeg`, `image/png`, `application/pdf`), and storing files in private S3 buckets with execution permissions explicitly disabled.
