## 1. Executive Summary

## 2. Identified Inconsistencies & Duplications

### 2.1 Points Calculation Signage
*   **Issue:** Master point definitions in `discipline_types.default_points` are positive integers. However, violations increase demerit totals while rewards decrease them.
*   **Risk:** If developers map points directly, rewards could end up adding to a student's demerits.
*   **Mitigation:** The service layer must explicitly handle point math based on category type:
    *   `type === 'VIOLATION'` -> `cumulative_points += snapshot`
    *   `type === 'REWARD'` -> `cumulative_points -= snapshot`
    *   Point balances must be floored at `0` so that rewards cannot reduce active demerits below zero.

### 2.2 Shared Media Attachment Structure
*   **Issue:** `discipline_incident_attachments` is specific to the discipline module.
*   **Risk:** Duplicated attachment logic when other modules (e.g., teaching journals, student profiles) add file uploads.
*   **Mitigation:** In the future, migrate to a global `media_attachments` table with polymorphic columns (`attachable_type`, `attachable_id`). For Sprint 1, we will keep the dedicated table to limit database changes but design the controller and service patterns to easily support future migrations.

## 3. Future Scalability Problems (10-Year Horizon)

### 3.1 Point Recalculation at Scale
*   **Issue:** Calculating a student's active points balance requires summing the point snapshots of all verified incidents in the active cycle.
*   **Risk:** As historical data grows over multiple years, reading and summing tables for every dashboard load or student search will create database bottlenecks.
*   **Mitigation:** 
    *   Implement an asynchronous job or trigger to cache active point totals on a summary table (`student_discipline_summaries`).
    *   Define a year-end point cleanup process that archieves old incidents and moves carried forward points to a starting balance record.

## 4. Security Risks

### 4.1 Attachment URL Vulnerabilities
*   **Issue:** Accepting direct file URLs from client requests presents a risk of malicious links or Server-Side Request Forgery (SSRF).
*   **Risk:** Users could submit paths pointing to local files or malicious domains.
*   **Mitigation:** 
    *   The API must only accept file keys generated by a secure upload service.
    *   Ensure that all media files are saved in an isolated Object Storage system (e.g., S3/MinIO) and served via secure presigned CDN URLs.
    *   Validate MIME types and enforce file size limits at the gateway layer.

### 4.2 Cross-Class Teacher Data Exposure
*   **Issue:** Regular teachers should only see discipline details for students they actively teach.
*   **Risk:** Teachers could access full behavioral profiles of students from other classes by guessing IDs.
*   **Mitigation:** Enforce ownership checks in the service layer:
    *   Ensure that users with role `Teacher` can only request timelines for students enrolled in classes they are assigned to in `subject_teachers`.
    *   `HomeroomTeacher` access is strictly scoped to the class they manage.
    *   Only `SuperAdmin`, `SchoolAdmin`, and `Principal` have school-wide read permissions.

---

## 5. Performance Bottlenecks

### 5.1 Verification Transaction Locks
*   **Issue:** Verifying an incident runs a transaction that updates the status, logs point snapshots, checks thresholds, and inserts sanction logs.
*   **Risk:** In large schools with high parallel activity, long-running database locks will cause API request queueing.
*   **Mitigation:** Keep transactions minimal:
    *   Status updates and point snapshots run inside a quick transaction.
    *   Sanction threshold evaluation and log generation run asynchronously via a background task queue (e.g., BullMQ or Bun's event loop) to release connection threads quickly.
